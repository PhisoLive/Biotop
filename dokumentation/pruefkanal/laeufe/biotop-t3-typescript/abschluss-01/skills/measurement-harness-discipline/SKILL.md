# Measurement harness discipline

For work where a **measured number decides something** — a benchmark gate, a perf regression threshold, a scoring harness, an A/B comparison, any "did this get better" verdict. The failure mode is never "we forgot to measure"; it is measuring the smoothing, the outlier, or the wrong denominator, and then defending the conclusion for weeks.

For a **read-only inventory / Bestandsaufnahme**, inspect the existing state rather than starting a new campaign. Deliver newly measured scope, implementation/runtime distinctions and reconciled totals; use earlier reports as provenance, not as material to repeat. Follow `references/read-only-inventory-and-reconciliation.md` for the ordered collection and accounting procedure; calibration steps below apply to new comparisons, not to an inventory.

## Procedure

1. **Define the acceptance boundary before dispatching work, then build the harness.** Name the core mechanisms, executable completion criteria, hard budget, and explicitly deferred work. For a repair, put scoring rules, per-test regression checks, and valid probe/countercase pairs ahead of ancillary work; a growing green-test count is not the deliverable. Decide what is measured, how many repetitions each point needs, how repetitions collapse, and what counts as meaningful change. Changing that measurement plan later requires a new series, not a retroactive tweak.
2. **Calibrate the noise floor first.** Run the harness repeatedly against the *unchanged* subject and record the spread. Do this before setting any threshold. See `references/noise-floor-calibration.md` for the concrete recipe and constants.
3. **Derive the threshold from that measured spread**, never from a guessed constant. A fixed "±15 % is noise" is a guess; it is simultaneously too tight for a jittery subject (real work dies on noise) and too loose for a stable one (real regressions pass).
4. **Re-calibrate per subject/area, not once globally.** Noise is a property of the workload, not of the machine alone. Different areas of the same system routinely differ by an order of magnitude in jitter.
5. **Prove each self-check can pass and fail before trusting a campaign.** Pair every calibration assertion with an executed countercase that must make that same assertion false; testing only rejected candidates does not prove the checker works. Keep these checks in a discoverable automated suite and retain their execution evidence. See `references/self-check-battery.md` for the paired-probe procedure, result validation, isolation, and accounting.
6. **When the subject of measurement is itself a gate or filter, measure it on its own decisions.** Residual-share metrics collapse under a working suppressor. See `references/gate-effectiveness-measurement.md` for the two numbers that do work, how to rebuild the decision-time baseline, and how to account for the gate's cost.
7. **Verify every number against its source before publishing.** Re-query the database/file/log for each figure in the writeup; do not transcribe from working memory. The figures that survive unchecked are the ones sitting in prose next to a correct table — a count written as "six consecutive runs" or a result mentioned without its record id reads as context rather than as a claim, and gets recomputed by the reviewer instead. Every figure in prose needs an enumerated row with its record identifier somewhere in the same document, or it does not get stated.

## Always-on rules

- **Honor an explicit scope reduction without erasing findings or lowering thresholds.** Stop out-of-scope workers, quarantine their partial or late deliveries, and retain each finding with its evidence, unresolved status, and named destination. Keep the old broad review failed; a later scoped pass certifies only the retained criteria, not whole-system correctness. Reopen a deferred issue in the current repair only by showing how it breaks the retained core and presenting that evidence to the owner. A small subject's size alone is not proof that a defect is unreachable.
- **Collapse repetitions with the median, never the minimum and never a single value.** The minimum rewards downward outliers: it pins the recorded best at an unrepeatable low, and every later comparison then reads normal behaviour as a regression. A single value measures whatever the machine was doing that second.
- **Form spread BETWEEN measurements, never WITHIN one.** The median smooths within a measurement — that is its job. Spread computed over the raw repetitions of one measurement therefore measures the smoothing, not the subject. Feed the spread function the list of already-collapsed measurement values. Where the codebase allows, make the within-level call raise rather than return a plausible wrong number, so the mistake is visible at write time.
- **Distinguish an outlier from noise, and preserve its identity until removal.** A value many times the median is a machine hiccup, not subject variability. Remove it using its original value or sample identifier, remeasure once, and record both readings. Round only the display: matching an unrounded sample against a rounded outlier list can leave the outlier in place and skip the required replacement. Folding the stall into the spread then permits genuine regressions.
- **Cap the tolerance, and treat exceeding the cap as a finding, not as a tolerance.** Past some point the measurement is not noisy, it is broken or the workload is non-deterministic. Report that; do not silently accept a threshold so wide it can never fail.
- **When a gate is missed repeatedly, change the producer, not the limit.** A quality threshold that the generator cannot reach is a statement about the generator. Fix what produces the measured artifacts — feed it what it already produced and require something new — and re-run the identical computation. If the intervention does not move the number, that is a finding about the generator, never grounds to lower the bar.
- **A failing check proves a deviation, never its direction.** Which side is wrong is decided only by a crash inside the subject or by a declared contract — never by the failure alone. Absent both, a failing artifact encodes an opinion about desired behaviour and must keep whatever standing it had; promoting it on failure alone lets any later change silently mint new blockers that then kill genuine fixes. This is the same figure as keying duplicates on location instead of on the claim, and fixtures on name instead of on a set marker: judge the substance, not the surface event.
- **Block at the smallest unit that is broken.** If one area's measurement is untrustworthy, block candidates whose actual effect reaches it, while allowing independently measurable areas to proceed; halt entirely only when nothing is trustworthy. Preserve semantic regression checks across all areas rather than hiding neighbour damage with the timing exclusion. State every skip with its measurement in the report, never silently.
- **A repeat-offender counter needs its time span.** Three flags within one session point at the machine; three across different days point at the workload itself. The same count means opposite things — carry the timestamps and say which reading applies.
- **A machine verdict taints the whole window, not the flagged unit.** When the repeat-offender reading points at the machine rather than the workload, every timing figure produced between the first and last flag is provisional — including the areas that passed calibration, because an unsettled machine perturbs all of them equally. Emit the caveat as its own reported line naming the window, not as a footnote on the blocked area.
- **Pin the calibration subject per gated system and seal it.** Every self-check needs a concrete object to act on (a specific boundary, fixture, or contract); choose it once, record it with a checksum, and reuse it unchanged. Re-picking per run means each calibration measures a different thing and cannot be compared with the previous one. If the object disappears or its checksum moves, that is a finding — log it, seal a replacement explicitly, and never let the harness quietly select another.
- **Seal the candidate population before the rate it will be judged by exists.** Where the headline number is a detection rate over a generated set (mutants, probes, fuzz corpus), freeze the set first — deduplicated, screened, checksummed, with the rate written into the sealing record as *not measured*. Once a rate exists, every later change to the set tunes the population to the metric: dropping candidates nobody catches, or generating more until the number clears the bar, both yield a defensible-looking figure that measures the selection. If the screen cannot yield the required count, the gate stays red and the count is not negotiated downwards. The screen is also not class-neutral — report the rate per candidate class, because a toolchain that rejects one whole class reshapes the admitted population. See `references/candidate-population-sealing.md` for the generation, screening and sealing order.
- **A screening failure is never a detection.** A candidate that the compiler, loader or schema check rejects was never presented to the detector, so it belongs on neither side of the detection rate. Carry four separate counts — generated, deduplicated, screened out with the screener's own evidence, admitted — and make the screening result unambiguous in the return shape: "screen ran and the candidate does not build" must be distinguishable both from "the candidate was caught" and from "the screener failed to run". Same three-way split as the infrastructure-versus-content rule below, applied at generation time.
- **Prove each self-check's verdict and its sensitivity.** Validate required result keys, types, and non-empty mechanism evidence before asserting the verdict; never turn a missing field or an empty observation list into a zero score or a passing default. Require the named rule or failing item, not rejection alone. Then execute a countercase through the same checker that must make its assertion false, and directly verify that the named violation disappeared; another false term in an aggregate is not that proof. Record execution validity separately from the boolean verdict: a missing subject, collection error, or infrastructure failure is not a successful negative control. Read both reasons before publishing; a check that can only pass checks nothing.
- **A self-check must not mutate the population it audits.** When a probe exercises a *real* rule against the *real* store — an ageing sweep, a promotion pass, a cleanup — the rule fires on genuine records too, and the measurement has then altered its own subject. Scope every such probe to its injected fixture before running it; whatever it still touched must be reverted before the next measurement and logged as reverted. Same figure as barring fixtures from the learning stores, one level up: there the check poisons what the system learns, here it edits what the check is measuring.
- **Enforce a self-check's stated precondition in the fixture; a declaration is not a control.** Where a check's validity rests on something *not* happening — no live network call, no write to the real store, no paid model invocation — sabotage that path so any attempt fails loudly, instead of asserting the absence in a docstring or a comment. Sabotage the boundary the subject crosses (the network primitive, the credential lookup, the store handle), never the unit under test: replacing the very method being examined makes the check tautological, and it then passes for a build that does the forbidden thing. Two further steps make the sabotage evidence rather than assertion. **Prove the unsabotaged call actually crosses the boundary** — run it once without the block and show the far side answering (any response, including an auth rejection, proves the connection formed); a block whose call would not have gone out anyway is vacuous and passes for free. And **assert on the sabotage message, not on its exception type**: the layer under test usually catches whatever the boundary raises and re-wraps it in its own error class, so a type-based assertion fails while the block is working perfectly, and the natural next move — loosening the assertion — is the one that hides a real escape.
- **Harness fixtures never feed the system's learning stores.** Injected regressions, probe candidates and self-check artifacts must be barred from every store the system later learns or decides from (run history, cross-subject knowledge, preference models). Once the self-check runs before *every* campaign the contamination compounds: an injected regression starts blocking genuine work, an injected pattern gets handed to unrelated subjects as experience. Bar them at each store's own write entry point rather than at the call sites, and keep them visible in the raw records — only the learning reads exclude them.
- **Identify fixtures by a field the creator sets, not by their name.** A naming convention is a promise the next author breaks: a probe written under a new prefix walks straight past a name check. Set an explicit marker at creation and test that marker; keep name matching only as a fallback for records written before the field existed. Same failure class as keying a duplicate check on location instead of on the claim.
- **Cross-subject knowledge must be stored as patterns, not as instances.** A record naming concrete files, functions and identifiers does not apply to a different subject, and a consumer is right to ignore it — measured: zero cross-subject citations with dozens of instances on offer, two citations in five after the same records were abstracted to named-entity-free sentences. Abstract each accepted change once, at write time, into one sentence saying what was done and why it worked; keep the instance alongside as evidence but present only the pattern across subjects. Never force a citation via a mandatory field — that manufactures pretextual references, which are worse than none. Reserve a fixed minimum share of the presented window for the cross-subject block: a subject with a long own history otherwise crowds the foreign entries out by sheer volume, and the same change then reads as effective on one subject and useless on another purely from pool size.
- **A pre-probe must run the gate's own entry point, one layer up from the helper.** Dry-running the measurement function that the gate calls internally omits the gate's replacement, sealing, history and verdict logic, so a green pre-probe there says nothing about the gate — and the gate then blocks on the run you spent the pre-probe to protect. Identify the function the gated command actually invokes, call that one against a throwaway store, and repeat it enough times to see whether the blocked set is stable or moves between attempts.
- **Cost totals across forked stores must be keyed on the buchung, not summed per store.** Copied or branched ledgers share the ancestor rows byte-for-byte, so adding the store totals multiplies the common trunk by the number of branches — measured: 26.37 summed against 9.09 actual, with 8.64 of trunk counted three times. Hash each entry's own identity (run id, timestamp, provider, model, tokens, amount, purpose), count identical entries once, and publish trunk, branch-only and unique totals separately. The same forking makes run ids ambiguous: the same id in two stores names different subjects, so every run reference carries its database path.
- **A sealed instrument binding proves bytes matched, not that they persist.** Checksums recorded at run time verify against the working tree and keep verifying while that tree exists; uncommitted files carry no history, no provenance and no way for a later subject to obtain the exact state. Report the version-control status of the instrument alongside the binding (committed at which revision, or N files changed and M new), and when downstream work is meant to build on the changes, put the decision to commit to whoever owns the shared line rather than committing on your own initiative.
- **When the owner does authorise the commit, land each accepted state as its own commit before the work built on it.** An approved state and the next campaign's changes squashed into one commit lose the boundary the approval was given for, and no later subject can check out the state that was signed off. Test separability first: hash the delivered archive against its own packing record, then compare its contents against the last commit — if the archive contains every committed file plus additions, the approved state is reconstructable and two clean commits are possible. If it is not reconstructable, say so and make one commit with an honest description rather than inventing a boundary. Going forward, every acceptance and every frozen instrument gets its own commit at the moment it is frozen.
- **Rebuilding a tree from an archive stages deletions for everything the archive omits.** A delivery archive is a snapshot of one scope, not of the whole repository, so `add -A` after unpacking it silently removes untouched neighbouring work that was never part of the campaign. Read the staged deletions before every such commit and restore any file the work did not actually touch. Back the whole repository up before tree surgery, and after restoring the working state verify it by checksum file-for-file rather than by eye — a restore that reports success and a restore that is byte-identical are different claims.
- **When a new guard lands, sweep for what got through before it.** The unguarded period already wrote records; removing them is part of shipping the guard, with a log of what was removed and why. A guard that only works forward leaves in place the damage it was written to prevent.
- **When a defect turns out to be an instance of a class, sweep for the class in one pass.** A hardcoded assumption that held while only one case existed — one language, one backend, one schema version — sits in more than one place, and finding the places by letting one gated run die per instance is the slowest possible search: each instance costs a whole run, and a one-shot gate gives that run back to nobody. Trace the live path for the new case first (cheap, certainly relevant), then sweep the untraceable remainder statically, then fix every unguarded hit in one commit and land the sweep as a test. Resolve each raw hit to guarded, unguarded or unreachable before calling any of it a finding — a hit whose guard sits two frames up, or whose pattern appears inside a case-neutral list, is not a defect, and reporting it as one buries the real one. See `references/defect-class-sweep.md`.
- **Gate by withholding the input, and test both routes.** When a precondition fails, return no usable object so the next stage cannot run, rather than a flag the caller may overlook. Prove invalid input stops before downstream side effects and valid input actually reaches the next stage; an always-refusing stub is not a completed gate. For calibration gates, exercise the real verdict consumer with inputs where measured and fallback tolerances disagree, so a disconnected calibration result cannot masquerade as enforcement.
- **For every duty there must be a named command.** Obligations the rules impose — aborting an invalidated run, halting on budget — need their own first-class entry point in the tool and its interface. A duty reachable only through improvised means (process kills, ad-hoc statements against the store) is either blocked by the safety layer or bypasses it, and both disappear once the path exists. Keep the normal protections on that command; the fix is a sanctioned route, never a weakened guard.
- **Classify a refused command, then re-request or halt — never route around it.** A command stopped by the execution layer is one of three things — an approval prompt that expired or was denied, a policy/filter block, or a refusal by the model — and each has exactly one correct response: re-request the approval, or halt and hand the decision to whoever owns the run. Quote the refusal verbatim together with the command it refused and say which of the three it was, on what evidence. Then change **nothing** about the command: not the wording, not the invocation form, not a different command reaching the same state, not another route to the same effect. An "equivalent plain form" is the trap — swapping an env-var prefix for a `cd` into the same directory loads the same code from the same place, so what was removed is the pattern the scanner recognises, not the risk it was flagging; the run then proceeds unapproved while looking approved. Only the run's owner may change what requires approval. Rephrasing past a refusal is indistinguishable from evading a policy block and destroys the one signal that would have identified which layer objected — and it must be reported as a fault even when the outcome turns out harmless.
- **A rule that blocks on an unresolved condition needs a path that resolves it, or it is a deadlock.** Guards of the form "unknown state ⇒ refuse everything" are correct at the moment they fire and permanently fatal afterwards, and the pressure then lands on weakening the guard — which is the one repair that must not happen. Build the exit as a *resolution* instead: establish the unknown from the authoritative source, and where it cannot be established, record the worst admissible value so the doubt is charged against the budget rather than forgiven. Clear one blocking record at a time, never release siblings, and keep the resolved amount subject to the same ceiling — a clearing path that cannot bankrupt the run is a bypass wearing a gate's name. See `references/provider-failure-accounting.md`.
- **Retry only failures the external system itself marks retryable, on a cap and wait fixed in advance.** A rate-limit or overload response carrying its own retry indication is a wait condition; an unmarked error is an outright failure on attempt one, and retrying it spends the retry budget on every genuine outage. Never retry a refusal or an empty answer — those are decisions, not disruptions — and a timeout stays a failure whatever caused it. Book and protocol every attempt, and place the retry beneath the accounting entry point so each attempt still passes the budget pre-check. The countercase that matters is an error *without* a retry marker failing immediately; testing only the retryable case proves the loop exists, not that it is selective. See `references/provider-failure-accounting.md`.
- **A pre-check that cannot form an opinion abstains; it never raises.** Guards that run *ahead* of the real judge — duplicate-work detectors, similarity screens, cache lookups — routinely hit inputs they cannot analyse (an unapplicable change, an unparsable artifact, a language the extractor does not handle). Raising there converts a per-candidate finding into a campaign abort, and the judge downstream already classifies that same input correctly as a rejection. Return the empty answer instead: no target, no match, no opinion. This does not weaken the guard that motivated the raise — refusing to *guess* a target with the wrong language's syntax is achieved by returning nothing, not by throwing. Mirror image of the rule below: an infrastructure crash must not be dressed as a content verdict, and a content verdict must not be escalated to a crash.
- **A checker's search root and exception lists are arguments, never module globals.** A sweep, linter or guard whose subject is read from a module-level constant at call time cannot be aimed at a fixture tree: patching the constant from the outside misses the read, the countercases silently re-scan the real subject, and both the sensitivity and the selectivity case then pass for reasons that have nothing to do with the fixture. Pass root, allowlist and exception table in as parameters and keep the module constants only as the production default.
- **An infrastructure failure must never be returned as a content verdict.** When a call errors — bad credentials, unknown provider, timeout — raise it; do not fold it into the same return shape as a legitimate negative answer. Otherwise a batch of crashes publishes as a substantive result ("0 usable, N rejected") and reads as a finding about the subject. Any tally that mixes them must report the three outcomes separately: produced, genuinely rejected, failed to run.
- **Inference from prose is a word statistic — confine it to low-stakes subjects.** Deriving a structural fact by counting what co-occurs in documentation finds what is mentioned together, not what carries load. Acceptable for practice subjects; for anything with real consequences require the fact to be declared explicitly in configuration, and halt with a request for it when missing rather than guessing.
- **State the denominator in the same sentence as the percentage.** A share is only meaningful against the population the rule names. Computing it against a conveniently larger set (all rejections instead of the tests actually produced) can understate by an order of magnitude and invalidates the conclusion retroactively when a reviewer recomputes it.
- **A negative finding carries the coverage of the scan that produced it.** "Not present anywhere" is only as strong as the set actually inspected: a sweep over live processes, files or hosts routinely fails to read part of its population (entries that vanished mid-scan, permission denials, skipped paths). Report hits as *x of y inspected* with the unreadable remainder named, and inspect the one instance that decides the question by name on top of the sweep. An unqualified absence claim resting on a partial sweep is the same error as a share without its denominator.
- **Under a "measure, change nothing" mandate, prove it with before/after state rather than asserting it.** Snapshot checksum and mtime of every file the work could touch plus the counter of whatever it could consume, repeat at the end, and publish both. Inspect connection helpers and probe setup before invoking them: a helper named "connect" can migrate tables, and a UI check can replace a real user's credentials. Use direct read-only connections or isolated copies rather than production helpers with setup side effects. When something did move, report it with its cause even when the cause was the user or an unrelated process — a mandate to change nothing is a claim about the system's state, not about your intentions.
- **Separate built, historically exercised and currently running.** Map requirements to implementations, implementations to recorded executions, and current activity to live process/service evidence. A persisted run status is not process liveness; a missing namesake module is not a missing function. If the current source already contains later work, label that chronology rather than presenting it as the requested earlier state.
- **Separate test artifacts from executed checks.** Report collected cases, executed outcomes, assertion counts, print-only examples and tests of the subject under improvement as different populations. Neither a script named "self-check" nor an exit-zero list of expectations proves an automated test passed; a failed collection setup does not prove zero tests exist.
- **Which configuration is *in effect* is answered by the outgoing request, never by the config file or a status command.** A declared default, a per-conversation override, a resolver's prediction and the payload on the wire are four different rungs of evidence; name the rung every claim stands on, and treat a read-back of the file as "configured as", never as "running on". When a setting appears to revert by itself, the question is which scope holds it, not whether the write landed. See `references/runtime-configuration-verification.md` for the evidence ladder, the clamp check, and how to read credential-pool state.
- **When the only instrument for a value requires altering the run, present the choice instead of choosing.** Enabling a dump, raising a log level or restarting the service makes the intervention part of the measurement and can destroy the exact question being asked. Say what each option can and cannot show, and let whoever owns the question decide — never silently intervene, and never silently substitute a proxy for the value you could not measure.
- **A gate cannot be measured by a rate whose denominator the gate itself shrinks.** When an intervention suppresses the very artifacts a residual-share metric counts, the better it works the fewer items carry the number — at perfect suppression the metric is undefined. Measure a suppressor on its own decisions instead: false-positive rate and leak-through rate against every decision it made. Keep the residual-share gate for a subject where the intervention is not acting on the denominator. See `references/gate-effectiveness-measurement.md`.
- **Check that the sample can resolve the threshold before reporting a pass.** With two items only 0 %, 50 % and 100 % exist — no value can land near a 20 % line, so the line is untested whatever comes out. A number that cannot fall on either side of the bar is not a weak pass, it is **not measured**; say that, and name where it will be measured instead. Same duty as reporting a check without a subject rather than letting it pass.
- **A limit whose configuration is absent or zero must refuse to start, never read as "no limit".** Budgets, quotas and ceilings wired to an environment variable or config key routinely default to `0` and are then treated as unset-therefore-unbounded, so the hard ceiling silently does not exist while every report still names it. This is the vacuous-check family again: a bar with no value is not a permissive bar, it is an absent one. Validate at startup that each limit is present and positive and abort otherwise — and treat *setting the variable* as fixing one instance, never as fixing the defect. Verify by reading the limit back through the code that enforces it, not from the shell that exported it.
- **Two runs that differ in more than one respect cannot isolate either.** Changing the component and the starting state together yields a difference attributable to neither. When the second variable was unavoidable (the new component needs a populated state to act on at all), say so explicitly and downgrade the claim to "consistent with" rather than "caused by".
- **Audit against the state at decision time, not the end state.** A produced artifact typically writes its own key into the very store the audit queries, so a post-hoc "was this already present?" check finds every artifact as pre-existing and reports a system-wide failure that never happened. Reconstruct the store as of each decision (prior contents plus decisions recorded earlier in the run) and exclude the artifact's own entry.
- **Audit leak-through against the whole store, not against the item's own declaration.** "Does this artifact repeat what it said it would do" and "does this artifact repeat anything already held" are different questions with different answers — measured: zero by the narrow reading, two by the correct one, and the narrow reading was what let the gate be reported as passing. Scope every filter audit to the full population the filter is supposed to protect. A narrowed scope produces a green row that is technically true and substantively wrong, which is harder to catch than an outright error.
- **When a counting error is found, re-run the corrected count over every figure that used the old counting.** Fixing only the figure whose absurdity exposed the bug leaves the same error standing in the neighbouring rows, where it is now harder to spot because one corrected value vouches for the rest. Correct the whole series in one pass and list which published numbers changed.

## Pitfalls

- **Place a harness's TMPDIR outside every recursively copied subject.** A sandbox that copies the subject into a temporary directory beneath that same subject recursively copies its own output; an apparent product failure is then a harness failure. Set PYTHONPATH and TMPDIR on each test subprocess, reject hard-coded production import paths in compatibility wrappers, and rerun the corrected red case before changing the product.

- **An audit must reuse the audited component's own derivation, not a re-implementation of it.** Writing a second, simpler version of how the component identifies things — parsing headers instead of applying the change, skipping the filter it applies to its inputs — measures something adjacent and manufactures discrepancies that then get published as unexplained differences. Import and call the component's function; if it is not callable in isolation, that is the finding to report. When an audit and the component disagree, suspect the audit first and settle each case individually before writing "differenz offen" into a report.
- **Never pair two event streams by order of occurrence.** Reconciling stage-A records against stage-B records by "next unclaimed B after each A" assumes one-to-one; pipelines routinely fan in (several per-area actions collapsing into one per-item verdict) or interleave unrelated entries between the pair. The mismatch then surfaces as a phantom gap — "two items produced nothing" — and the first explanation invented for that gap is usually also wrong. Join on the identifier that actually links the stages (item id, call id, the intermediate record each side references), and when the counts still differ, name the fan-in factor rather than the missing items.
- **An age or expiry counter conditioned on successes never fires near the ceiling.** "Retire after N accepted rounds" stops counting once the subject is good enough that rounds stop being accepted — exactly the state where retirement matters most. Measured: zero retirements across five campaigns, because the campaigns had one accepted round each. Condition ageing on attempts, and check any threshold rule for the same shape: if the counted event becomes rare precisely when the rule should trigger, it is the wrong counter.
- **Validate the sample contract before calibration and again after replacement.** Enforce the specified count, not merely enough values to calculate a range; require finite positive timing values and reject booleans. After outlier removal and the bounded remeasurement, require a complete valid sample with no remaining replacement request. Otherwise block the affected area even if a numeric tolerance looks plausible. A filter or retry can invalidate the count that an earlier guard checked.
- **Output carrying content the command cannot produce is contaminated — discard all of it, including the plausible parts.** When captured output opens with lines from an earlier, unrelated step, do not reason about which half is real: re-run from a clean working directory under a fresh script name, confirm with a minimal echo that the channel is clean, and only then use the result. Publishing the believable remainder of a contaminated capture is how a wrong number enters a report already vouched for by correct neighbours.
- **An evidence channel refuses an oversized payload loudly; it never truncates.** Clipping a result to its last N bytes leaves output that still parses, so the consumer reads a smaller well-formed result and the loss is invisible at every downstream station. Return an explicit transport error carrying the limit and the measured size, and when a legitimate subject exceeds that limit, raise it deliberately rather than letting the harness decide which half of the evidence to keep.
- **Re-measuring a subset means running the full-population scan and filtering its result.** Handing only the subset to the scanner changes what the scanner sees — dead-code, cross-reference and dependency analyses all resolve against the whole project — so the re-measured value silently stops being comparable with the baseline it is meant to update. Call the same whole-population entry point the baseline used, then select the requested entries from its output.
- **A detector keyed on source-text patterns reports zero the moment a second language arrives.** Matching `def name(` to find tests, or one suffix to find modules, degrades to an empty result rather than an error when the subject is written in another language — and an empty result reads downstream as "nothing found", not as "detector does not apply". Route recognition through the per-language adapter or parser, and add the wrong-language case to the detector's own test set.
- **Require executed, completed evidence at every test, sandbox and measurement reader.** Skipped, aborted, empty or missing evidence is invalid, never green; absence of failure is not evidence of execution. A JUnit `<skipped>` testcase (including pytest xfail records) has neither failure nor error and must not become `ok=True`; partial success text does not override an aborted runner. Carry the inner pytest exit status through wrappers before interpreting JUnit; a wrapper can exit successfully after an interrupted child wrote a partial report. Preserve an executed assertion failure as a content result, but propagate infrastructure invalidity rather than a false verdict that another consumer can reinterpret as success. Preserve execution validity through each consumer and test the original read path with both unusable evidence and a genuinely completed control. When this defect is found, inventory all readers of the same result class instead of fixing only the first parser. Distinguish a legitimately empty findings list from a missing execution: only a completed scan with explicit coverage can support the former.
- **Pair JUnit with completion evidence from the same pytest run when it gates admission.** Exit 1 can mean fully executed assertion failures, maxfail truncation, or an explicit abort; compare collected items, call reports, and completed teardown reports, and require every expected test file to contribute. A green neighbouring file cannot vouch for an empty or deselected required file. Keep legitimate executed failures measurable, and never truncate the failure-ID list consumed by per-test Pareto or test admission.
- **Validate scanner completion according to its actual protocol.** Inject corrupt/absent outputs through the real scanner subprocess and measurement consumer, not only a disconnected parser. Preserve clean zero-result controls: Vulture's completed exit-zero empty stdout is legitimate, unlike an empty Bandit JSON document. Exercise supported non-scoring findings too, so a new output guard does not misclassify valid scanner reports as infrastructure failure.

- **Suspect your probe before the system under test.** A probe that perturbs something *within* one measurement is erased by the harness's own aggregation; vary it *between* measurements. When a deliberately broken input fails to trip the detector, prove the probe is actually broken before touching the detector.
- **A fixture where the right rule and the wrong rule agree proves nothing.** Before trusting a precedence rule ("prefer A, fall back to B"), check whether the test subject happens to make A and B select the same thing — the test then passes whatever the code does, including the version that ignores A entirely. Construct a case where the two diverge and assert that A's answer wins.
- **Do not re-cut categories between reports.** Reusing a breakdown's category names with different boundaries makes two reports non-comparable while looking comparable. Keep the earlier categories, and if a category must change, show both cuts.
- **Every breakdown must reconcile to its stated total and accounting cut.** Publish the sum; if it does not reconcile, name the difference and its cause rather than quietly dropping a bucket. Run IDs do not freeze their ledger rows: later calls can be charged to an old run. Compare historical and current row sets before invoking rounding, then show both the sum of rounded subtotals and the rounded raw total. When historical membership is reconstructed from counts rather than retained IDs or a snapshot, label it as a reconstruction; matching rounded amounts does not prove unique membership.
- **Read a one-shot gate's precondition block before paying for the stages in front of it.** Calibration and sealing stages routinely record their own failure under the run's id and then refuse re-entry by design ("no re-calibration"), so a missing input is not a retryable error — it kills the run, and everything already spent on that run still counts against the hard ceiling. Before invoking such a stage, enumerate every raise-branch in its validation path, satisfy each one, and verify the state it actually reads: it queries the store, so an artifact sitting in the working tree proves nothing until the command that registers it has run. Satisfying every structural branch is still not enough when one precondition is a **measured number** that can simply come out too high: dry-run that measurement standalone first — the *gate's own* entry point (not the helper it calls, which omits the verdict logic), same repetition count, same verdict function, writing nothing to the store — and only open the run once the value clears, repeated enough times to show the verdict is stable. A one-shot gate gives no second reading, so the first time the real stage computes the number must not also be the first time anyone looks at it.
- **A measurement change mid-campaign invalidates the campaign, not just the next data point.** Abort, record why, restart from the same starting snapshot. Patching results after the fact is the one unrecoverable error. This binds on changes made for reasons that have nothing to do with the measurement: the seal covers whole instrument files, so a budget-accounting fix or a deadlock repair touching a sealed file kills the run exactly like a tuning change would. Before opening a gated run, sweep for every instrument defect you already know about and land them all in front of the sealing stage; once one becomes necessary afterwards, take the run's death rather than patching quietly and letting a later stage discover the binding no longer matches.
- **Read the runner's own error streams after every campaign, not just the result store.** A driver loop that requests more units than the run has left produces a refusal the core never records — the store shows a clean series while a per-unit `.err`/stderr file carries the abort. Writing the report from the store alone therefore omits it entirely. Sweep the campaign's error files for non-empty ones before publishing (the inverted pattern — empty result file beside a filled error file — marks them), and report even a consequence-free abort with its cause; "fail loudly, never silently" binds hardest on the aborts that changed nothing, because only those are tempting to leave out.
- **Attribute effects to the component you actually measured.** "The expensive calls were all from component A" is a claim to verify by grouping the log, not to infer from which component you were thinking about.
- **Verify what actually blocked before anyone builds a rule on the diagnosis.** A cause named in passing in a status report gets adopted as fact and turned into policy — and a policy built on the wrong cause weakens the wrong thing. Read the refusal, find the code path, then report. Correct the diagnosis explicitly when it was wrong, even after the rule derived from it has been accepted.
- **A reviewer's finding can be sound in the concern and wrong in the mechanism.** Accepting the mechanism along with the concern imports their error into your correction and propagates it further than the original mistake, because it now arrives endorsed by both sides. Verify the proposed cause against the records before adopting it, and in the response separate the two explicitly: which part held, which part the records contradict, and what the actual mechanism is. The same applies to your own first explanation of a gap a reviewer found — check it before publishing rather than after.
- **When a fix looks ineffective, check how much input the test case actually offered.** An intervention that supplies better material only helps where enough material exists; measuring it on the subject with the sparsest pool reads as zero effect. Measure on the subject the change was meant to serve, and publish both readings with their pool sizes so the dependency is visible.
- **An intervention can improve the mechanism while the headline rate stays flat.** If the change makes bad cases *detectable*, they now appear in the count instead of passing unnoticed — the rate holds while the outcome improves. Report the composition beside the rate (how many were caught and rejected, how large the largest surviving cluster is), or a real improvement is filed as a failure.
- **A zero in a store's metric column may mean unpopulated, not measured-as-zero.** Cost, duration and score fields are frequently written only by a code path that did not run, leaving the default. Before reporting "cost 0", check whether *any* row in that column is non-zero; if none is, the column is empty and the honest report is "this source carries no figure", not a zero. Reporting the default as a measurement invents a precise-looking number out of a missing one.
- **Adding a field to an existing store needs an explicit migration.** Create-if-missing schema calls skip tables that already exist, so a new column never appears and every read of it errors. Follow the create with an inspect-and-add step for columns introduced later.
- **A structured-logging helper's own parameter names collide with payload keys.** Passing a payload field that shares a name with the logger's signature (kind, id, category) raises "multiple values for argument" at the moment of logging — i.e. inside the error path, where it masks the original fault. Nest the payload under one key, or prefix payload names.
- **Separate cost subtotals without excluding spending from the hard budget.** Report calibration, self-checks, and the measured campaign separately, split into sandbox/compute runs and paid model calls. Count all of them, including failed attempts and retries, against the task's hard ceiling; a separate subtotal is not free budget. Measure harness cost before committing to a larger subject instead of assuming a fixed cost per named probe.
- **Attribute harness cost from counter differences, not tags alone.** Sample the counter before and after each step, including nested calls with other tags, and book the difference. Maintain a latest-result view for acceptance so reruns do not inflate the number of completed checks, but retain every attempt's raw evidence and cost in the ledger. Replacing a result must never erase charged work.
- **Do not scale harness cost by unit count without checking what actually repeats.** If calibration measures every area inside one pass, more areas lengthen each pass but do not add passes — multiplying runs by area count invents a number. State which quantity scales, and measure the large subject rather than extrapolating from the small one.
- **Build the on/off matrix before crediting any component.** When several changes ship in the same window, tabulate runs against which components were active and attribute a movement only to what differs between adjacent rows. Credit claimed for a component whose gains already appear in the run before it was enabled is the single easiest claim for a reviewer to overturn, and it discredits the parts that were genuinely earned.
- **Two readings spanning a wide range establish spread, not effect.** Where a downstream consumer's behaviour is the measured quantity, separate what is mechanically demonstrated (the input it was given changed, verifiable and stable) from what it did with it (variable across calls). Publish both, and do not summarise the pair as one effect until enough readings exist to distinguish the two.
- **Name a gate after what it measures, not after the mechanism behind it.** A line called "minimum share" that actually tests "at least one occurrence" promises more than it checks, and every later reader recomputes the stronger claim and finds it unsupported. Either rename the line to the property it tests, or measure the property the name states — and put the choice to whoever owns the criterion rather than settling it yourself.
- **A gate on a declared intent cannot be repaired by rejecting divergent output — pair it with a gate at the point of admission.** Where an actor announces what it will do and the gate rules on the announcement, nothing binds it to that announcement; measured: one of two produced artifacts did not match its own declaration, and two of three admitted artifacts carried a key that was already held. Rejecting whatever diverges from the declaration discards the genuine finds the actor turned up while working, so it is the wrong fix. Add a second, **deterministic** check at the entry point to the store, keyed on the artifact actually produced, and give the two gates separate metric lines: the declaration gate is measured on calls saved and honest abstentions, the admission gate on leak-through. Keep the declaration–execution divergence as a reported diagnostic, never as a blocking criterion. See `references/gate-effectiveness-measurement.md`.
- **Gate negotiated changes on the cumulative applied file set, not on the declared origin or the latest partner alone.** Reuse the real change application function, union the changed areas with their transitive dependents, and repeat the gate on the final admission payload. Carry earlier accepted partner adjustments into every later pair check; a missing measurement verdict after a precheck refusal must never count as a successful negotiation.
- **A gate must sit at every route into the store, not only the main one.** Secondary intake paths — the rejected-but-retained bucket, the quarantine list, the "does not count" category — usually still write a key that later decisions read, so an artifact entering there is indistinguishable downstream from one that came through the front door. Measured: half the leak-through arrived via the secondary path while the primary one was clean. Enumerate the write sites before declaring a gate complete.
- **A corrected figure is a second claim until it has its own pass and fail case.** A number that ran wrong → corrected → wrong again is the normal shape: the first value was right for the wrong reason, the correction removed one of two compensating errors. Before publishing a revision, construct one case that must produce the new value and one that must not, and say whether they came from the real run or from a constructed fixture.

## Reporting

- Report old and new side by side when a methodology fix changes a number, and name the mechanism ("spread 47 % → 11 %: the old figure used the minimum of repetitions and folded in a machine stall"). A corrected number without its cause reads as a contradiction.
- When the fix invalidates an earlier *justification* as well as an earlier number, say so: a rule adopted on the strength of a figure that turned out to be an artifact still needs re-grounding, even when the rule itself survives.
- Mark measured, inferred, and decided separately. "Confirmed by execution" requires the attached output; otherwise say what was read but not run.
- Report a failed check as failed, in the first sentence of the item, not as a qualifier at the end.
- **Every delta names the baseline it was computed against, and no delta survives its baseline moving.** "11 changed plus 29 new" against one reference and "49 files" against the next are both correct and read as a contradiction. Once an intervening step advances the base — a commit landing, a snapshot being sealed, a population being re-screened — recompute the earlier figures against the new base rather than repeating them. Put base and result in the same line, and when a reader challenges a mismatch, show both computations instead of defending one.
- **Deliver the artifact, and make it reachable in the message.** Where results live in a folder or report rather than the chat, every summary carries the full locator — complete path or URL, uncut, on its own line — plus a checksum and the item count it covers. A reviewer reads the artifact, not the message, but cannot open what the message only alludes to.
- **Long result summaries get truncated in transit.** Past roughly a dozen itemised findings, split deliberately into numbered parts and repeat the locator in *every* part; a part that arrives without the locator is unusable on its own. If the reader reports a state that differs from yours (different count, different checksum), name and explain the difference rather than re-sealing the artifact to match.
- **Publish every companion file's locator, not just the report's.** A checksum whose manifest has no reachable address cannot be recomputed by the reader and is decoration; list the report, the file manifest, the checksum file and the cost sheet, each as a full uncut locator on its own line.
- **Package source dotfiles explicitly when the delivery server does not serve them.** Keep their original bytes and names in a verified archive, optionally provide non-dot download aliases with an exact original-to-download checksum map, and verify every published payload over HTTPS. Never relax the server's dotfile protection for a code delivery. If a sealed publication has unreachable members, retain it as a failed attempt and publish a numbered replacement with a correction notice instead of silently changing its manifest.
- **Never overwrite delivered bytes; make supersession explicit in the next revision.** Publish a numbered correction notice naming the changed claims and the old and replacement documents, and link it from the new report and file list. Do not prepend a notice to an already sealed file, which would invalidate its checksum. In an undelivered draft, correct superseded sections in place rather than leaving contradictory conclusions. If a reviewer sees an older version, verify the served bytes once and publish the correction at a new numbered address instead of arguing about caches; query-string busters are not an immutable revision.
- **The title of a delivered document is part of its content.** A report headed "parts one to six" that actually contains parts one to nine will be read as incomplete, and the reader is right — they read the heading, not the body. Update the title and the summary table in the same edit that appends a section.
- **Withdraw your own claim as soon as the measurement turns, without being asked.** When a re-measurement moves a figure across the acceptance line, state in the first sentence that the criterion is not met and that you are not requesting acceptance — before explaining, before describing what was built. A finding against your own work that arrives volunteered is worth more than the same finding extracted by the reviewer, and burying it under the build report reads as an attempt to have it both ways.
